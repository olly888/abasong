# Abasong UI/UX 深度评审与升级方案

2026-11-07，洛杉矶。V3.4 提案，供评审与下一轮原型制作。现行品牌与组件基线为 V3.3。建议先升级发布需求、司机圈发帖和「我的」，再同步收敛地图与需求详情。优先处理容易填错和找不到下一步的问题。

评审依据为本机 App 源码、产品规则、当前浏览器原型及前轮 Dasher 截图。用 390×844 的浏览器视口走查了发布入口、两种需求表单、发帖和「我的」。原型数据为合成示例。以下观察分别标明来自 App 源码或原型，原生动效、手感及真实用户耗时仍需另行验收。[V3.3 现行设计系统](Abasong_设计系统_V3.3_现行规范.md) · [产品基线](../../产品基线.md) · [两场景发布规则](../product/Abasong_V3.2_两场景发布与公寓卡片优化补充.md)

## 1. 当前问题与优先级

| 优先级 | 发现 | 对用户的影响与处理 |
| --- | --- | --- |
| P0 | 仓库场景的原生表单同样默认「尽快到场」。已定规则要求仓库场景由发布人选择到场时间。两场景在代码里也都默认「约数」，而代送规则默认确定件数。 | 对齐两套预设。进入未来日期时清除未经确认的时间，要求明确点选。原生「其他日期」目前先写入后天，建议改为直接打开日期选择器，取消时原值保留。 |
| P0 | 原生核对页只在自定义时显示下架时间，并将账号要求和送完要求合写在一个摘要中。部分已填选填条件如经验、理货或线路没有完整回显。 | 核对页必须呈现实际下架、送完要求及所有已填的接手限制。每组可点「修改」直接返回对应位置。 |
| P0 | 当前原生校验以底部的一条错误为主。派送区、快递公司、取件区缺失时会共用一句提示。 | 错误落在对应字段下，点击核对后定位首个出错项，保留已填内容。地址服务失败、资料冲突和发布结果未确认另有提示。 |
| P1 | 原型两张发布表单在补充条件收起时，滚动正文约为可见区的 2.4 倍。原生表单依次铺开六组，价格在靠下的位置，基础条件与低频条件的视觉重量接近。 | 合成三个主要区块。将影响司机是否接手的条件放在报价之后，默认值用一行摘要呈现。低频设置按需展开。 |
| P1 | 原生仓库地址选定后还要单独选取件区域，更换地址时会清除区域。派送区域与快递公司并排，长地名在窄屏和大字下容易挤压。 | 区域与承运商可自适应换行。优先复用经过核对的仓库与取件区域关系，遇到多义或无映射时才请发布人选区域。 |
| P1 | 发帖里的内容标签、配送区域、关联需求都使用相近的选择器样式。原生会在打开编辑器时一并请求地区和两版需求列表，失败共用重试。 | 正文和图片优先。标签直接点选，地区与关联需求降为两个轻入口，分别加载与重试，普通文字帖可以直接发。 |
| P1 | 登录态「我的」确有独立标题条，原型在 390 px 宽时约占 64 px，下面还有较高的个人资料行。登录态源码未发现单独的促销横幅，游客原型有欢迎区。 | 将标题条和个人资料视觉收敛为一个身份区。用户所指横幅若来自特定构建，进入原型前对照该构建确认对应组件。 |
| P1 | 需求详情已有数量与报价并排，但派送、取件、时间、身份和接手条件散落在多个标签块中。 | 核对页和详情使用同一信息顺序。列表先展示司机做决定所需的信息，完整地址放在有权限的详情。 |

## 2. 发布需求的新版结构

首页和司机圈继续从同一个「发需求」入口进入场景选择。入口保留「仓库缺人，找司机」「送不完，找人代送」两张整行可点的选项。副标题分别说明「司机到仓库取件」「请同行接手部分或全部包裹」。同一账号可以发布任一场景。表单采用**一屏顺序填写，下一屏核对**，让经常发需求的人熟悉同一套路。

### 仓库缺人，找司机

```text
‹  仓库缺人，找司机
发布身份  个人 / 已选团队名                         更改

取件与派送
仓库地址  [搜索或选择本次仓库]
派送区域  [选择区域]
快递公司  [SwiftX] [GOFO] [SpeedX] [UniUni] [其他]

到场安排
接手日期  [今天] [明天] [选日期]
希望到场  [选择时间]

需要多少人、怎么报价
需要司机  [−]  1  [+]
总待送件数  [约数] [确定] [待确认]   [输入件数] 件
报价  [按件] [按线路] [联系议价]   $ [输入金额] / 件

接手要求  联系确认 · 送完时间待定                    更改
补充条件                                            展开
                [核对需求]
                 保存草稿
```

仓库候选项显示仓库名或门牌、城市和完整地址，选中后就地换成可核对的摘要。候选过少或失败时，显示明确的手填入口。手填展示门牌与街道、城市、州、选填邮编，再明确确认这次取件地址。已核对的取件区域作为摘要，允许更改。地址变化只使与旧地址绑定的取件区域和确认失效，保留派送区域、承运商、报价、人数和日期。

同一个仓库反复使用是 DSP 流程里值得继续观察的场景。已有「复制需求」可作为快捷路径。后续如加入「最近使用的仓库」，只显示本人有权查看的已确认地址，点选后仍确认本次取件。近期仓库的需求频率先用试点观察确定优先级。

### 送不完，找人代送

```text
‹  送不完，找人代送
发布身份  个人 / 已选团队名                         更改

交接与派送
取件方式  [途中交接] [仓库取件]
交接地区  [选择区域]         具体地点在联系后确认
派送区域  [选择区域] [与交接地区相同]
快递公司  [常用快递公司点选] [其他]

什么时候接手
[今天] [明天] [选日期]   今天可选 [尽快] [约时间]

剩余包裹与报价
[确定件数] [约数] [待确认]      [输入件数] 件
[按件] [按线路] [联系议价]      $ [输入金额] / 件
接手要求  可分担 · 送完时间待定                        更改
补充条件                                            展开
                [核对需求]
                 保存草稿
```

「与交接地区相同」由本人点选。切换成仓库取件时只替换地点子表单，并清除旧交接地点的关联状态。数量待确认时隐藏数字及最低件数。用户选择「整批接手」时，立刻要求切换到确定件数，并说明为什么。普通代送流程省去司机人数控件，仍由双方确认接多少件。

### 控件、字段与交互规则

| 字段 | 默认控件与显示 | 校验和状态 |
| --- | --- | --- |
| 发布身份 | 一行「个人」或团队名称。符合权限时才出现身份选择。已发布内容显示原发布身份。 | 进入团队资料后回到原草稿。团队资料保存完成后仍让用户确认「代表团队发布」。历史快照按原规则保护。 |
| 快递公司／地区 | 快递公司用短选项，超出可用宽度时自然换行或打开列表。地区数量较多时用带搜索的选单。 | 「其他」才展开快递公司名称输入。仅从已有可用地区中确认映射，城市名称或 GPS 点不直接变成已选地区。 |
| 日期／时间 | 「今天」「明天」直接点选，「选日期」打开系统选择器。仓库默认今天，时间待选。代送默认今天、尽快。 | 选未来日必须明确时间。切换到今天时保留本人确认过的有效值，或按场景重新选择。取消选择器、回改、跨午夜和洛杉矶夏令时分别验收。 |
| 人数／件数 | 仓库人数用步进器，点击数字可输入大值。仓库默认约数，代送默认确定。数量用单选，数值在其下。 | 待确认没有伪造的 `0`。整批要求确定件数，明确数量时每人最低量不能超过总量。 |
| 报价 | 用「按件／按线路／联系议价」三选一，金额输入旁即时显示 `$` 与单位。 | 议价时隐藏金额。切换计价单位需要重新核对输入金额，避免把每件数额直接当成整线价格。空金额提示填写或选议价。 |
| 接手要求 | 将可分担、承运商账号、需 DSP 确认、当天／次日送完集中为一行摘要，点开后再选。 | 摘要同时显示已设的硬性条件。硬性条件在核对、详情与报名确认中使用同一组文案。 |
| 补充条件 | 默认收起。按「货物与线路」「截止时间」「其他说明」分组。 | 理货状态、经验优先用点选。线路号和私下付款约定保留输入。显示自定义下架时，区分接手、送完与下架三个时间。 |

建议将固定底栏第一步改为「核对需求」，最终确认按钮使用「确认发布」。编辑已发布需求用「核对修改」和「确认保存」。核对时应看到实发身份、完整仓库地址或大致交接地区、实际接手日期、数量口径、人数、报价单位、已设置的硬性条件、送完及下架安排。默认下架采用服务端有效规则，有最迟接手时间时以该时间为准，否则是接手日结束。原型与 App 的时间摘要须用同一规则验证。回改后保留草稿，展开目标组并恢复焦点。首次失败、重试、版本冲突、重复点击继续走现有保护，提示分别放在字段附近或主操作附近。[服务端发布时间规则](../../apps/api/src/requests/request-v2-input.ts#L218) · [字段错误识别指引](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)

## 3. 司机圈发帖

```text
‹  发布动态
写一条动态
[分享配送经验、问个问题，或记录路上见闻]

[＋ 添加图片]  0/3      已添加后在此预览、移除
[配送提问] [经验分享] [路上见闻]    可选一个
+ 添加配送地区
+ 关联我发布的需求

                  [发布]
```

- 正文是首屏主体，保留 2,000 字上限。空白时按统一规则展示不可发布状态和原因，字数接近上限时才提示。图片为选填，显示数量、添加、预览和移除。选图继续调用现有系统相册和拍摄，收起键盘时底部发布操作仍可达。
- 三个已有标签直接点选，可再次点取消，默认留空。地区仅在司机明确添加时显示，已选值可直接清除。将「关联我的支援需求」改为「关联我发布的需求」，选中后呈现一条可移除的引用摘要，详情仍遵循对象权限。
- 地区与需求选项按各自入口加载或复用会话内已加载结果。列表失败时，只在对应入口给「重试」，普通文字或图文可继续发布。引用请求在确认发布前重新检查可见性。已经结束的关联需求显示结束状态，相关历史帖子可按现行规则保留。
- 区分「图片上传失败」和「发布结果未确认」。前者在图片附近标出可重试或移除的那张图，保留已上传图片。后者保留本次载荷，使用现有幂等机制重试。离开有内容的编辑器时继续提供保留草稿或放弃。
- 发布入口保留「发动态」与「发需求」两项，让文本经验交流和可报名的真实配送需求各有清晰路径。正文或图片涉及门禁资料时，继续沿用现行分享入口与资料保护规则。[司机圈首版规则](../product/Abasong_V3.2_司机圈定位与最小社区补充.md)

## 4. 「我的」以及关联页面

**「我的」顶部直接从头像与显示名开始。** 状态栏下只保留安全区与正常页边距，头像、姓名、「编辑资料」和箭头合成一个身份行。取消占据整行的可见「我的」标题条和大面积装饰区，底栏继续显示「我的」，页面保留辅助技术的页面名称。游客用紧凑的登录区，登录后用姓名完成身份识别。

```text
（头像）我的显示名                                ›
       编辑资料
接活状态                         [开关]
今天 3:00–6:30 PM · 2 个区域     修改时段

                [＋ 共享门禁码]

我的公寓      我保存的 · 我共享的                  ›
我的发布                                           ›
我的报名                                           ›

邀请司机                                           ›
我的团队      已有团队名／可填写资料                ›

```

保持已确认的「个人资料→接活开关→共享门禁码→个人工具」顺序。未启用时只显示「暂不接活」，开启后明确显示本次时段与区域。进入设置又取消时保留原状态。团队入口沿用现行显示资格，邀请使用普通列表行；已保存公寓、发布和报名共用行高与分组边距。团队、邀请和报名各用语义不同的图标。设置页和二级资料页保留可理解的返回标题。[我的与团队规则](../product/Abasong_V3.2_我的与团队资料补充.md)

## 5. 品牌与组件规范

- **品牌蓝用来指路。** `#1769FF` 用于每屏主要动作和品牌资产。点选控件用浅蓝底、深蓝文字或对勾。地图定位、建筑高亮、仓库点、焦点框分别定义角色，首批可映射现有蓝阶，用形状或描边补充色彩信号。表单正文和普通区域采用中性色，使报价、地点和主按钮最容易被找到。
- **让品牌出现在有意义的时刻。** 登录、邀请、海报和对外落地页使用正式字标，沿用等比、留白与最小宽度。日常操作页用共同的蓝阶、图标线宽、字重和状态反馈表达品牌。「我的」顶部留给账户身份。
- **用组件建立一致性。** 优先复用 `PageFrame`、`ActionButton`、`Field`、`SelectionField`、`BottomSheet` 和地图外框。补齐常驻单选组、地址摘要、可修改核对行、字段错误、区域搜索选单和轻量附件行。短选项适合直接点选，长列表才进入选择器。输入控件继续用在地址、价格、数量和正文。
- **让版式服务于读数。** 以现有 20 页边距、48×48 最小热区、52 主按钮、正文 16/24 和常用圆角为起点。建议组间用 24、字段间用 12–16。数字与单位相邻，数量、时间与金额可用等宽数字排版。长城市、团队名和双语地址允许换行。大字号下并排行先纵向重排，次要信息仍可读。
- **原生质感从行为做起。** 底栏适应键盘和安全区，日期与照片沿用系统控件，系统返回先退出核对层，按钮按下、加载、成功和失败都有一致状态。第一批使用现有 RN／Expo 和浅色底图验收；夜间地图另做一屏小样，核对底图、蓝点、地址、门牌和浮层的可读性。[V3.3 组件与品牌规则](Abasong_设计系统_V3.3_现行规范.md) · [DoorDash Prism](https://careersatdoordash.com/blog/design-language-system-theming/) · [Apple 安全区与布局](https://developer.apple.com/design/human-interface-guidelines/layout)

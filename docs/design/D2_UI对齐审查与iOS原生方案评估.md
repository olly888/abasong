## 结论

当前只能认定主要结构与部分规则已接入，**不能认定全部页面达到原型的视觉和交互质量**。核心问题是业务组件和控件细节没有逐页收敛，以及原型/页面规格存在部分不同步；现有证据不足以支持“必须重写为SwiftUI”。

建议保留React Native/Expo的双端业务页面与既有Mapbox原生集成，先完成一次明确的UI对齐批次。对日期时间、选择菜单、确认与弹层使用适合平台的原生交互；确有必要时，可在现有工程局部嵌入SwiftUI。不以全面换框架替代页面设计与验收。

## SwiftUI、React Native与当前工程

React Native不是在iPhone里放一个网页。其View等核心组件映射到原生视图，当前工程用TypeScript/React组织页面；SwiftUI是Apple平台的声明式原生UI框架。两者都需要开发者落实字体、间距、层级、动效和无障碍，框架不会自动复制Abasong原型。[React Native官方说明](https://reactnative.dev/docs/view)，[Apple SwiftUI](https://developer.apple.com/swiftui/)。

当前@rnmapbox/maps是社区维护的封装，底层接Mapbox官方iOS/Android SDK；Mapbox的SwiftUI Map同样包装其MapView。地图数据、分类覆盖、GPS准确性和地址匹配仍取决于数据、系统定位与业务逻辑，不能以选择SwiftUI作为这些问题的解决证据。[Mapbox RN说明](https://docs.mapbox.com/help/glossary/maps-sdk-for-react-native/)，[Mapbox SwiftUI说明](https://docs.mapbox.com/ios/maps/guides/swift-ui/)。

| 方案 | 对本项目的影响 | 本次判断 |
|---|---|---|
| 保留RN，修业务组件与视觉 | 继续复用双端页面、状态和已验逻辑；修正本次明确偏差，仍须做平台适配 | 当前主方案 |
| RN业务页＋局部原生控件/SwiftUI | 复用业务流程，为iOS改善选择器、菜单或sheet；需要对应的Android体验和新的构建/交互验证 | 适合小范围验证，按控件决定，不预先全量替换 |
| iOS业务UI全部改为SwiftUI | 服务端/数据库可复用，但iOS页面、导航、状态衔接、鉴权/地图/OCR适配及回归需大量重新落实；Android仍需维护自己的UI实现 | 当前不推荐。没有测量证据显示现有方案无法达到目标，不为“更原生”口号承受全面迁移成本 |

局部采用SwiftUI在技术上已有官方路径：与当前Expo58对应的@expo/ui文档提供SwiftUI组件，并通过Host与React Native互嵌。本项目尚未安装@expo/ui；本次不宣称已有兼容性验证。实施前应先试一个日期时间控件和一个面板，再决定是否引入。不能把“可集成”写成“无需新构建或无风险”。[Expo58 SwiftUI文档](https://docs.expo.dev/versions/v58.0.0/sdk/ui/swift-ui/)。

## 建议的对齐批次

此为供本次评审的建议，尚未开始修改应用，不擅自切换技术栈。

1. 统一H01/P01/P03/P08/P09/P10/U01基准：每页明确正常、空、错误/无资格和编辑状态；原型落后时先同步，保留已批准的新规则。
2. 整理业务页面容器和按钮/字段/面板变体，先修底部操作栏、输入选择方式和图标。原生系统习惯可与Web原型不同，但信息层级和业务结果一致。
3. 先交付“发布一个临时需求”和“报名并查看管理”两组样板；日期/时间及面板优先做原生交互小样。使用公开/合成资料，不等待真人短信。
4. 用相同数据、状态、逻辑尺寸和字号并排检查原型与iOS；区分原型外壳/系统状态栏/地图数据差异，不能以无数据空态替代目标状态。
5. 检查键盘不挡主动作、点击反馈、左边缘返回、面板取消、滑卡/地图手势、长地址/完整密码及贡献人、放大字号和读屏。Android同批核对共享组件的影响，真机出口继续单列。
6. 收敛样板后继续B3。每批交付同时记录功能检查与UI结果；没有测过的交互保留待验，不再把JS导出或后端测试数量当作设计验收。

是否进一步引入SwiftUI由这个小样的真实结果决定。当前审查建议先修实现并增强原生交互，不重做品牌、不全面迁移、不重写已通过的后端。

## 1. 首版范围

| 内容 | 当前裁决 |
|---|---|
| P01发需求 | 只展示“仓库缺人，找司机”“送不完，找人代送”两个入口 |
| P03发布/编辑 | 同一表单，场景决定默认值和必要字段；整线/部分是任务范围，人数是缺口，取件方式是地点条件 |
| 车辆/其他专用求助表单P04 | P1后置，不出现在首版发布入口/评审可用目录；旧记录可读，不回滚实际接口。可通过已有司机圈文字求助 |

首版价值顺序仍为查码/贡献/纠正→配送协作→次级积累和互助，不把新增列表或增长功能当作核心出口前置。

## 2. 两种场景与默认值

| 项目 | 仓库缺人，找司机 | 送不完，找人代送 |
|---|---|---|
| 使用情况 | 临时缺勤、爆仓、当次需要额外司机，也可提前约明天 | 已领包裹送不完，联系同行接手部分或整线 |
| 身份 | 统一个人账号；不强制先建DSP团队 | 同一规则；DSP也可发布代送需求 |
| 默认取件 | 仓库地址 | 途中交接的大致地区，可改仓库 |
| 默认时间 | 今天，发布者选择希望到场时间 | 今天、尽快；改未来日期后必须选到场时间 |
| 数量 | 默认约数，明确总待送件数、需要人数；也能选择确定/待确认 | 默认确定件数，可改约数/待确认；整线接手需确认件数 |
| 分配 | 不从总件数÷人数推导承诺给每人多少件 | 部分/整线在补充条件中，不再成为一级入口 |

两个场景是同一张配送需求的填写预设，不是长期招聘、排班或自动派单。统一账号可以使用任一入口。“我能接活”继续U03声明，不再创建另一种找人帖子。

## 3. P03信息与操作

默认主视图按六组组织：

1. **派送安排：**派送区域、快递公司。主视图不重复展示地区与长地址。
2. **取件地点：**仓库/途中交接可切换。仓库完整地址必填，名称选填；候选带入已核对的取件地区；手填地址保留明确城市，不能拿附近点猜坐标。途中交接只选大致地区，具体地点双方联系。
3. **接手时间：**今天/明天快捷、日期和希望到场；今天可选尽快。未来日期不保留“尽快”。
4. **任务量：**确定/约数/待确认；有数字时正整数。仓库场景显示人数，代送场景不强制填人数。
5. **报价：**金额与每件/每线路单位，或明确选择联系议价；不填金额不能冒充免费。付款约定选填，平台不结算。
6. **接手条件：**账号/转派确认条件和送完要求，报名之前可见。经验若作为硬性条件填写，也要出现在核对/详情中。

补充条件默认收起：仓库名、线路号、最迟接手时间、代送整线/部分、每人最低量、配送经验、理货状态、付款约定、其他说明与自定义下架。没有启用复杂条件时不逐项要求选择。本人发布身份显示为紧凑可修改摘要；已发布来源锁定，团队改名不重写历史。只有本人明确选用并成功发布后，才可为下一次预填该身份，不能自动把司机切成DSP。

固定底部“核对并发布/核对并保存”及草稿沿用现有组件；核对页保留场景、身份、地址、接手、任务量、价格单位、硬性条件、送完要求和下架时间。取消核对回原表单；失败保留本次输入；重复确认不重复发布；编辑遇版本变化必须重新核对。首版发布耗时仍需真实司机/DSP观察，表单高度下降不证明完成率已提高。

## 4. 三种时间与数量口径

**接手时间**表示希望何时到场/开始取件；**送完要求**表示当天送完、可次日或联系确认；**需求下架**只决定何时停止展示，不代表配送承诺。

原型明确默认规则：有最迟接手时间时，默认到该日该时间下架；没有时默认接手日23:59（洛杉矶），发布者可在补充条件中修改。核对页显示实际下架日期/时间。非法先后关系阻止提交，过去的接手时间不可发布；“尽快”使用本次时钟，不借旧草稿日期续期。这是目标规则，尚未更改现有API的starts_at/expires_at语义。

确定、约数、未知必须贯穿核对、摘要、详情、报名、本人管理、动态来源、公开摘要及草稿复制。未知不是0；约数不是精确剩余上限；不确定量不能自动均分成每人承诺。未知量的仓库需求仍能声明可接能力并报名，件数可选；报名不自动减少需求人数或包裹量，不代表已接单。确定整线按明确整批件数处理。未知量只更新人数缺口，不让发布者填一个假的包裹剩余量。

## 5. 地址、地图与公寓卡片

仓库候选与手填地址沿用既有流程；修改地址清掉旧候选关联、派生取件地区和自动仓库名，保留其他填写。切途中交接清旧地址/位置并重新核对交接区。定位失败不阻断可读地址及外部导航；不生成假点，外部地图仍只在用户点击后打开。完整仓库地址仅按现有登录详情规则展示，不加入公开摘要/锁屏。

公寓卡收起仍为门牌28加粗＋街道20常规单行；城市左、近似距离右，内部距离依据/排序不变，无“至边界”文案。密码原样显示#/*和前导零，旁边只展示该条来源明确的门别；未知门别不补“大门”。门别是次信息，长标签可省略，展开看完整范围，不能挤掉密码。贡献时间与用户名继续保留，展开提示固定右下，整卡可点；无码/失败/无资格各自清楚，禁止用额外图标填空。

附近列表P1：复用同一200米候选及距离顺序，列表/地图同ID同选中；一行地址/城市/距离，点选后展示该公寓的有权密码；返回保持阅读。不得静默扩大全城目录、批量预读所有密码或制造“暂无资料”。首版不增加该入口，P1实施时单独核对读取策略、状态和无障碍。

## 6. 技术增量边界

独立原型复用已有层级、控件、仓库示例、版本和消息链路；不安装模块或调用真实发布服务。原型为兼容旧演示数据暂映射已有kind枚举，**不是生产数据迁移方案**。

实际开发D22必须先同步OpenAPI生成源/类型/增量迁移及事务权限：场景与任务范围分开，quantity_mode与可空件数、asap/接手时间、completion及expiry规则须版本化；未知量不能映射为0来绕过旧正整数契约。发现/报名/缺口/复制/来源通知与公共DTO一起处理，旧记录默认语义明确。所有授权仍由真实服务执行，合成状态不能证明安全隔离。公开DTO只增必要口径/时间，不包含仓库精确地址、联系人、位置或门禁。

D23为卡片局部布局与空门别处理，复用已有来源；D24为P1附近列表未实现项。实际App仍V3.1，不改令牌源，不引入SwiftUI重写或新品牌。

# DoorDash 司机端研究与 Abasong 借鉴方案

本文件是2026-11-04研究证据，建议部分不等于当前采纳规则。最新[E01–E12采纳表](Abasong_竞品与替代方案证据表_2026-11-05.md)与[产品基线](../../产品基线.md)明确：首版区域点＋当前结果，边界/全量统计/机会订阅另排；不能用第4节的早期推荐恢复为强制全城边界开发。

日期：2026-11-04，America/Los_Angeles。对象：Dasher 司机端，含 DashLink；不把消费者点餐端作为司机工具的主参照。依据为用户提供的9张真实界面截图、官方帮助/产品/工程资料，以及本仓库B4实现。**本文为设计研究和变更建议，尚未替换现行PRD、V3.1或开发排期，未修改业务代码。**

2026-11-04后续收敛：[升级总览](../Abasong_V12.1_产品设计技术升级总览.md)已将主方案定为区域点＋当前结果，区域面仅有来源对照。用户随后补充5张DashLink图，仓库取件时段/完整地址/地图导航有价值，已纳入[UP11取件补充](../product/Abasong_V12.1_仓库取件地址与导航补充.md)。截图没有证明复制交互；该操作为Abasong目标，不把候补/评分/预计收入搬入。本文其余研究仍保留当时建议范围。

## 1. 结论

优先吸收地图与对象联动、按当前情境突出一个主动作、明确的区域选择、时间与地域偏好，以及司机不常驻App也能收到相关机会的机制。

Abasong的主任务仍是核对门牌并读取/贡献密码，其次是当次支援协作。建议下一轮原型先展示“公寓近景”和“支援区域概览”两种地图信息层级，用现有公寓/找活/找人模式切换；维持首页/司机圈/我的三导航。

六边形有空间统计价值，但应先解决区域的业务含义、真实计数和选区后的操作。首版推荐有依据的服务区域轮廓＋数字标记；六边形密度层作为有足够空间数据后再验证的方案。

## 4. 地图语义：区域、热点、六边形分开

### 4.1 三者的含义

| 概念 | 解决的问题 | 在Abasong中的对应 |
|---|---|---|
| 起始/作业区域 | 在哪里开始、查看哪些机会 | 配送服务区域及司机愿意去的区域 |
| 热点 | 哪些地方近期或当前较活跃 | 有足够数据后，基于有效支援请求的分布汇总 |
| 六边形网格 | 用什么空间单元聚合和绘图 | 可选统计方法，不构成公寓、线路或服务区的事实依据 |

官方区域说明将红/灰/金色用于不同的司机进入条件，受到区域容量影响；而Hotspots另区分当前动态热点与近期历史热点，且不保证接到订单。[区域说明](https://help.doordash.com/en-us/dashers/article/new-dasher-navigating-reserved-zones)、[热点说明](https://help.doordash.com/en-us/dashers/article/how-can-i-find-hotspots-in-my-area)。

因此，截图中的灰色不能翻译成“没有建筑/没有地址资料”；Busy也不能直接翻译成“Abasong缺3名司机”。Abasong没有承运商全量运单和实时供需数据，只能表达平台实际掌握的需求、声明及其时间范围。

### 4.2 六边形与手机网络无关

用户所说的蜂窝展示可理解为蜂窝状六边形。手机状态栏的5G是网络连接，两者无关。H3是一种可将地理空间划分为六边形单元的索引系统。[H3官方介绍](https://h3geo.org/docs/)。

DoorDash工程文章确实介绍过在**消费者内容检索**中应用H3；这只能证明其存在相关技术应用，不能证明截图中的司机地图采用同一算法、分辨率或实现。[DoorDash工程原文](https://careersatdoordash.com/blog/taming-content-discovery-scaling-challenges-with-hexagons-and-elasticsearch/)。

### 4.3 推荐的展示方案

**首版：服务区边界＋有效数量。**

1. 远景显示少量服务区域名称与计数；选中区浅蓝填充、清楚轮廓，其他区域弱化。
2. 点区域后更新同一视图的列表/卡片；蓝点只代表本人真实位置，不随所选区域移动。
3. 放大后只强调当前区和相关需求对象；切公寓模式恢复建筑、门牌和独立公寓卡，不叠满支援分区。
4. 只有有来源、可解释的区域才绘制边界；没有边界时保留区域点，不能画一个随意圆形伪装真实服务范围。
5. 司机声明区域可能跨多个市界。不要直接描摹DoorDash专有经营区，也不能从截图反推本项目地区坐标。

**后续候选：六边形活跃分布。**

需要真实需求的可用空间依据、足够覆盖和稳定时间口径；按缩放选择聚合粒度。先用相同的合成数据比较区域边界与六边形，不因视觉好看就默认上生产。

现有请求主要绑定区域ID、司机绑定愿意去的区域；若把区域中心点转换成六边形，全部对象会挤在中心，制造不存在的精细密度。此时增加H3不会提升真实位置质量。即使使用六边形，也不能将一个人的可接活区域画成他正在那里的定位点。

### 4.4 Mapbox能做什么

Mapbox可用GeoJSON面、填充和边界线渲染自定义区域。[官方示例](https://docs.mapbox.com/mapbox-gl-js/example/geojson-polygon/)。这证明渲染能力；该网页示例不是本项目RNMapbox双端实现或验收证据。

Abasong的区域来源、开放需求、司机声明与热度含义由业务服务提供。开通地图账号不会自动得到“Abasong哪里缺人”、DoorDash的经营区或其热度数据，也无需为画六边形单独采购一种“蜂窝地图接口”。新增分析或搜索服务的权限与计费需另行核对。

### 4.5 相机尺度与真正的蜂窝网络场景

建议沿用当前公寓首次定位约17级、支援约14级作为洛杉矶测试起点。用户主动查看多个城市时，才进入更远的区域概览；选区后按有效边界适配视野，公寓近景回到建筑/门牌。具体级别由屏幕尺寸、选区大小和底部面板可见高度共同决定，不能按截图的像素尺寸硬套。公寓200米候选规则是地面距离，不由屏幕缩放级别改变；比例尺继续采用SDK实际英尺/英里尺度。

若用户也关心手机蜂窝连接：定位、底图、业务资料是三条不同链路。弱网时能看到蓝点或缓存底图，不代表本次密码/需求已经读取成功。原型要分别覆盖底图失败、定位不可用、资料读取失败和时段数据过期；不把旧地址密码带到新地址，也不据截图5G标志推断网络稳定。离线密码存储不属于本轮新增建议，需要单独的产品及权限设计。

## 5. 计数与时间：比颜色更重要

建议地图先显示可验证的事实：

- 找活：所选时间内仍开放的**需求条数**；人数、件数在需求卡单独显示。
- 找人：时段匹配且未关闭的**声明司机人数**；不写“在线”“就在附近”或“已确认到场”。
- 数据范围：明确当前筛选条件及更新时间；请求失败是不可用，不等于数量0。
- 未来时段不计入“现在可接”。若提供现在/今天/明天切换，服务端必须采用对应时间窗口，而不是只换一个标签。
- 同司机在多个区域出现是其服务意向；跨区总人数需去重，不直接相加。
- 明确关闭、账号停用、屏蔽与到期都要影响计数；返回列表不能继续显示已终止的旧对象。

**现有B4缺口：** `discovery-model.ts`的areaMarkers按当前加载列表计数，CollaborationHome最多加载5页×20项。它不是区域全部司机/需求总量。将其升级为区域全量数字或热度之前，需要独立聚合契约；短期可明确表述为当前结果，不能把100项上限当作市场总量。

聚合接口未来应按当前账号可见范围、时间和区域计算，并与列表使用同一筛选条件。缓存需考虑屏蔽及资格范围；列表读取和联系仍单独对象鉴权。首版不通过“需求数÷司机数”自动推断缺口：司机多区域声明、实际承运商资格及回应意愿都可能不同。

## 6. 预约模式：适配为当次可接活意向

官方预约流程可以选择日期、起始区域和时段；新的ODR试验群体又可能采用随时上线和建议繁忙时段。因此截图的“区域已满→预约”不能推广为全部账号的固定流程。[预约帮助](https://help.doordash.com/en-us/dashers/article/how-to-schedule-a-dash)、[现行ODR说明](https://help.doordash.com/en-us/dashers/article/overall-dasher-rating)。

Abasong推荐表达：

> 我明天下午可以去Pasadena支援，最多可接80件。

这是本人意向声明。DSP发布某日需求、司机报名、双方联系，继续使用现有对象和人工约定；没有库存席位，不应显示“预约成功、已保留线路”或阻止司机同时表达意向。首版不增加预约排班/抢名额/候补队列或自动占用司机容量的状态机。

建议优化现有U03：

| 内容 | 建议 |
|---|---|
| 日期 | 今天、明天快速选择，另保留系统日期选择器 |
| 时段 | 起止时间；跨午夜明确次日，不给出模糊的“今晚”承诺 |
| 地区 | 复用常跑区域，允许本次修改；首版仍为单次1–5区 |
| 件数 | 选填；DSP可据此发起联系，不能将声明件数当作核验产能 |
| 关闭/到期 | 关闭停止推荐；结束自动隐藏，后续不悄悄续期 |
| 回程 | 保存后回实际来源，保留选区/阅读，不增加独立导航 |

“常跑区域”是持久偏好，“明天可接活”是有期限声明，二者应区分。偏好用于减少填写，并不自动表示全天愿意接活。多时段、每周重复、日历同步暂不进入首版。

## 7. Flash Offers：最适合我们吸收的机制

官方Flash Offers支持司机未处于接单状态时接收机会通知，并可通过偏好和可用时段控制；具体可用性与市场/近期活动有关。[官方说明](https://help.doordash.com/en-us/dashers/article/flash-offers)。

对Abasong的启发来自用户已确认的微信群痛点：人很多，但司机没看消息、正在其他App工作或当时没空。

建议把现有可接活声明接到“相关机会提醒”，而非要求司机一直盯着地图：

1. 本人主动开启，选择愿意去的区域和本次时段。
2. 只针对真实开放、时间重叠的支援需求；不以“司机就在这里”为前提，不新增后台精确轨迹采集。
3. 通知简短说明区域/时间，点开重新获取当前需求条件；锁屏默认不带私人地址、联系方式、密码或消息正文。
4. 同一需求去重、限制重复提醒；关闭、到期、撤销和账号变化立即影响后续投递；不回应不扣分。
5. “已发通知”“供应商受理”“对方已读”分别处理；不能告诉DSP“已有8人看到”而只有8次发送请求。

报价详情放登录后的需求卡，体现区域、当次日期、件数/最低量、单价单位、取件地区及付款约定。最终条款及费用继续双方私下确定。承运商经验是自报信息，不把提醒筛选宣传为官方资格核验。

**落地前置：** B3已有设备/偏好和推送队列，但真实APNs/FCM/Expo凭据及送达仍未验。此建议不等于提醒功能已可对外承诺；首版先让声明和静态筛选易用，受控通知在真实送达验证后启用。短信替代会带来额外接入和费用，本轮不加入。

## 8. UI与交互设计吸收

### 8.1 吸收原则

截图1、2、6体现地图上保留上下文、底部面板完成当前操作；2025年的官方改版说明也将更大地图、简化首页及更准确落点作为方向。[官方改版说明](https://about.doordash.com/en-us/news/delivering-a-better-experience-for-dashers)。

Abasong可采用以下具体规则：

- 一层一个主要动作：有密码优先直读；无密码突出添加；需求优先看条件/报名；司机资料优先联系。
- 地图上持续可见定位；展开面板或键盘时工具与归属信息避让，不被底部卡覆盖。
- 相同对象的点、面、卡片和列表采用一致选中状态；重读不抢走主动阅读。
- 将区域边界置于底图之上、建筑/门牌等重要内容之下；切公寓模式关闭支援统计层。
- 选中用皇家蓝，背景图降低竞争；颜色配合文字/数字，不靠颜色区分无数据、加载失败与暂无结果。
- 详情和偏好使用清晰分组、固定主操作；默认简短，次要说明按需出现。

### 8.2 不照搬的细节

- 首页收入胶囊：平台不结算，现有资料不足以给出司机完整周收入。
- 左上抽屉和多个消息入口：保留三导航与统一消息中心，不同时新加通知铃铛与聊天两个入口。
- 巨型预约标题与满宽固定卡：公寓任务需要短暂查看，仍按已有独立滑卡及紧凑高度设计。
- 大片红色Busy标签：红色在现行V3.1已有危险/错误语义；需求急迫用明确截止时间和文字表达，不把区域选中都染成红色。
- 立即改成全深色：维持现行浅色基线，先检验地址/密码在户外、深色系统和地图上的识读再决定主题排期。
- 图2密集标签和长区域名：控制碰撞和显示优先级，突出所选区，不复制其遮挡问题。

## 9. 其他功能的边界

| 能力 | 研究发现 | Abasong建议 |
|---|---|---|
| DashLink | 一次取件多次配送，并有当天候补机制 | 研究取件区/配送区/车型和当次时段的信息组织；不复制承运商扫码/POD/候补派单 |
| Amazon Key | DashLink官方已描述对特定公寓的授权电子门禁接入 | 长期竞争研究要包含电子门禁；首版仍密码为主，无固定密码状态可表达，不做无合作基础的一键开门 |
| 安全工具 | 有专项安全服务与紧急响应合作 | 一般车辆互助必须标清边界，平台无相应能力时不复制安全专员/自动定位转发承诺 |
| 评分/等级 | 依赖其配送过程数据，规则可能因市场/账号不同 | Abasong不掌握完整配送履约，不造接单率、准时率或综合能力分；展示自报经验及真实可追溯反馈 |
| Peak Pay | 激励带区域和适用时间 | 清楚展示DSP实际报价及加价，不设平台补贴、奖金账户或收入保证 |

事实来源：[DashLink及Amazon Key](https://help.doordash.com/en-us/dashers/article/waitlist-faq-for-runners)、[安全工具](https://help.doordash.com/en-us/dashers/article/dasher-safety-faq)、[评分](https://help.doordash.com/en-us/dashers/article/overall-dasher-rating)、[Peak Pay](https://help.doordash.com/en-us/dashers/article/peak-pay)。

其中电子门禁是值得持续跟踪的替代方式，不代表所有公寓已接入、第三方可以直接调用，或共享密码工具已经没有价值。Abasong的跨承运商资料覆盖与低成本贡献仍需用首批司机的实际查码成功来验证。

## 11. 建议进入下一轮原型的优先级

这里的P0/P1为**建议优先级**，等待产品收敛后再进入正式开发计划，不直接覆盖B4/B5。

| 优先级 | 方案 | 原型/验收出口 |
|---|---|---|
| P0 | 公寓近景和支援区域概览分层 | 三模式切换信息与对象清楚，建筑/密码不被热图遮挡 |
| P0 | 区域选择、卡片及列表一致 | 点区→结果→详情→返回、拖图/定位均保持预期上下文 |
| P0 | 数量和时间语义 | 不混淆当前加载与全部、现在与明天、声明与在线 |
| P0 | 精简可接活：今天/明天、时段、常用区域 | 司机无需解释能开启、修改和关闭一次声明 |
| P0 | 情境主操作和空/失败态 | 不把错误当无需求，空区域有有用下一步，不增加页面提示堆叠 |
| P1 | 真实区域边界与独立聚合 | 边界依据清楚；账号权限、时间窗口和多区去重实测 |
| P1 | 自愿相关机会提醒 | 有偏好、去重、静默和失效规则，实际远程送达后才对外启用 |
| P2 | 六边形分布层/繁忙预测/等待时间 | 足够数据后与简单分区比较，不能用装饰网格替代证据 |
| 暂不纳入首版 | 预约席位、候补排队、等级、平台补贴、独立紧急调度 | 与现有数据能力和平台职责不匹配 |

原型研究建议同时做区域点与有来源的区域面的对比；所有数值使用同一份合成样本，标明示意，不拿某套更漂亮的数据制造偏好。六边形只作为概念对照，不成为必须开发的前提。

## 12. 下一轮任务验证清单

1. 公寓门外打开App，正确核对门牌、读码；相邻公寓最近的一张不是目的地时，能切对且不会串码。
2. 从查码切到找活，能解释区域边界与蓝点的区别；点区、切列表、进入详情再回来不迷路。
3. 选择明天的可接活时段，回首页知道自己尚未“现在可接”，并能关闭；偏好不会自动重新开启。
4. DSP查看明日需求的司机列表，能区分声明、已联系和确认合作；不能将报名数视为已到场人数。
5. 数据加载失败、过期或部分分页时，用户不把它理解为全市场无人/无需求。
6. 同一司机声明多个区域，统计不会误呈现多名司机；筛选日期和列表结果一致。
7. 真实通知接入后，司机在承运商App中也能按自己的时间/区域收到一次相关提醒，关闭偏好后不继续打扰。
8. 截图贡献、无密码添加和纠正仍保持简单；新地图设计不使它们退到更深层级。

小样本测试建议覆盖熟手司机、偶尔支援司机及DSP，观察实际操作和理解，不重复要求已经完成的需求访谈。此清单还未在真人身上执行。

## 13. 尚不能从公开资料确定的问题

- 截图所用司机底图、样式、网格精度、区域算法及其当前SDK供应商，不能凭视觉断言。
- 不同账号/市场/实验组合的完整预约与地图规则；官方新旧页面及截图本身存在差异。
- Abasong首批区域适合何种边界、何种提醒频率及是否真的需要热度层，需要原型任务与实际样本验证。
- 初期多少资料才足以形成司机的持续查码价值、跨承运商贡献质量及DSP回应率，不能从DoorDash的规模外推。

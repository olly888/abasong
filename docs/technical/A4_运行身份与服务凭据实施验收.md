## 实际故障与修复

1. 首次真实 PostgreSQL TLS 正确拒绝 `SELF_SIGNED_CERT_IN_CHAIN`。从 Supabase Database Settings 下载官方公开根证书，校验 SHA-256 指纹并仅加入 PG 客户端配置；保留主机名和证书验证。`pg` 的 URI SSL 参数会覆盖显式 SSL 配置，所以先严格验证 URI，再从副本移除 SSL 参数并传入固定 CA、servername、rejectUnauthorized。系统、AWS、HTTPS 和 D0 信任不变。[官方连接说明](https://supabase.com/docs/guides/database/psql)，[公开 CA 来源与指纹](../../packages/runtime/certs/README.md)。
2. Secrets Manager 首次写入被原全局 KMS Deny 阻断。按官方 FAS 机制，仅允许 Secrets Manager 通过 `aws/secretsmanager` 托管密钥执行标准加密；直接 KMS、业务密钥和秘密读取继续受限。真实 Access Analyzer 0 findings，七组模拟后原地创建新版策略，保留旧版本；五项写入实测成功。[官方加密与 ViaService 规则](https://docs.aws.amazon.com/secretsmanager/latest/userguide/security-encryption.html)。
3. ACM 请求暴露不完整 `DomainValidationOptions` 参数；删除该可选项，采用官方单域 DNS 请求形式，不创建 Route53 hosted zone。又核对到 ACM 需要其 AWS 托管 `aws/acm` 密钥元数据权限；核对实际 AWS 托管策略后，允许 ACM 的标准服务代理操作，grant 仍由 AWS 自身 ViaService、GrantIsForAWSResource 和 GrantOperations 条件约束；没有身份策略 KMS Allow，直接加解密、业务密钥及私钥导出仍受限。元数据修正七组、最终服务修正九组模拟及 Analyzer 0 findings；最终两份部署策略十四组模拟通过。证书实际签发及 DNS 结果仍独立核对。[官方证书资源](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-certificatemanager-certificate.html)，[ACM 私钥保护](https://docs.aws.amazon.com/acm/latest/userguide/data-protection.html)。

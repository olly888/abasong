# D1 本人贡献纠正、撤回与共享管理验收

2026-11-01，America/Los_Angeles。承接ADD-19；正常贡献直接共享，不增加人工逐条审核。

## 实现与产品反馈分开

本批实现本人来源管理的API、0008迁移、原生列表/纠正表单与合成原型。用户在Android补验后提出“不建议有撤回已经贡献的密码”。因此技术通过不等于该功能最终产品认可；普通撤回入口是否取消、误共享如何处理，保留为本轮产品讨论。当前代码仍有普通撤回入口，不宣称已经按新建议移除。

纠正将正确密码新增或复用并结束本人旧来源；多名贡献人独立，不改他人来源或旧密文/票。没有有效来源的规范码不再公开，记录保留用于历史与幂等。旧创建者来源结束时公开署名/排序时间使用仍有效的最早来源。个人列表只列一次来源，展示当前有效反馈，未实施的查看人数为null并隐藏。

## 数据与权限

0008仅在隔离本机D0应用：52张强制RLS表、8次迁移。临时测试库从旧创建/同码重复事件迁移，验证首次时间、归属、唯一来源、旧撤回不恢复及事件关联。未向Supabase/生产迁移。

列表和单项summary只查本人元数据；detail正文另需access.read，公寓/全局状态、过期及支持范围检查仍有效。纠正须access.contribute；撤回只须有效账号及本人active来源，资格到期不阻止结束自己的来源。其他账号ID为404，来源UPDATE RLS限制owner，事件继续追加。

同一owner写入串行，纠正目标与旧来源同事务；expected_version拒绝过时编辑，幂等收据只重放结果，不重复执行后续恢复的来源。旧收据operation/applied_version与当前source.version/status分开。

## 原生与原型证据

- iOS27/iPhone18Pro模拟器：正常账号“我的→我的公寓→我共享的”可直读本轮合成码及反馈；纠正来源声明→新码→返回共享tab。首轮实测发现返回后旧列表未刷新，修复为dismissTo带非敏感revision重新读取；第二次实际纠正立即出现新码及旧记录“本人已纠正”。
- iOS取消撤回保留密码；确认撤回后显示“本人已撤回”，本人正文立即隐藏。未删除其他TEST记录。列表操作改为一行，减少三枚大按钮造成的高度。
- Android API37模拟器：正常列表/固定公寓纠正表单实际观察；同账号iOS撤回Android正在编辑的来源后，Android提交收到“资料已更新，请刷新后重试”，输入及确认状态保留，旧版本不覆盖。
- Android正常纠正/撤回补验：用户对组合步骤回复“验证通过”，同时提出取消常规撤回的产品建议。工具随后看到2445首页及TEST-AND-FINAL#；清理前数据库仍有1个active来源，因此**正常纠正通过，Android最终撤回不单独标记已观察通过**。iOS撤回及服务端撤回已有独立证据，不能替代这一Android手势。
- 工具的Android点击/输入焦点不稳定；部分路径使用实际原生Tab/Return，随后正常完成路径由用户补验。没有用adb输入、客户端权限注入或合成适配器冒充认证业务。
- 开发热更新曾使effect的AbortController被清理后继续复用，导致表单停在busy；重建controller及提交意图修复，并以最终冷启动/类型检查覆盖。切账号/后台继续由SensitiveScreen清理明文内存。
- Chrome合成原型：本人记录/反馈、纠正固定地址和门别、旧状态与新码、撤回确认/历史、查看人数隐藏实际操作通过。它是合成数据，不证明服务安全或真实使用人数。

忽略目录`.tooling/contribution-management-acceptance/`保留界面证据；不将真实账号ID、凭据或司机GPS写入仓库。

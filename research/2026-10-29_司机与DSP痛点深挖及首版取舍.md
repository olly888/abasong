# Abasong：司机与 DSP 痛点深挖、产品价值与首版取舍

研究日期：2026-10-29。研究对象：洛杉矶尾程配送场景，以发起人三个月配送经历、已完成访谈和本轮公开资料核查为基础。

**核心结论：值得继续，但应把第一版收敛为“可靠进门信息 + 可成交的轻量找人”。司机圈与生活信息是后续关系价值，不能替代现场有效性与当地真实运力。当前漂亮的原型尚未证明真实公寓识别、资料覆盖、资料授权与司机响应链条成立。**

本文是研究与范围建议，不自动修改已确认的原型、排序或 PRD。涉及改变的产品规则明确标为建议，需结合实测再决定；不虚构本人拥有司机或 DSP 经历，也未声称进行新的真人访谈。

## 1. 证据分层与边界

### 1.1 已由用户一线经验支持

- 原 App 没码、码错、进不去公寓，直接拖慢当天配送；希望打开备用工具立刻看到正确公寓的可用信息。
- 扫描、路线、POD 和官方工作数据继续在承运商 App 中完成。
- 司机很忙，微信群人数不等于愿意且有空接手的人；时段、价格和是否看到消息影响响应。
- DSP 接受外部人选，真正需要区域/线路/人数/件价发布、经验与联系、长期合作关系。
- 司机愿意同行协作，休息时也可能看租车、租房、买车、保险、趣事和问题。
- 配送费用完全私下结算，平台不建设对账和收付系统。

### 1.3 仍是推断的内容

价格不足时的救援供给、下班方向、冷启动资料覆盖、重复合作与软件付费意愿，都需要通过真实任务和使用记录判断频率与影响。本文给出合理的待测假设，不将其描述成已证实的全美现状。

## 2. 如果站在配送司机的位置

我会关心四个结果：**少等、少走错、少接不划算的任务、按预期收工。**

### 2.1 被拦在门外

我不是想看一个公寓数据库，而是希望在眼前这一栋、这一扇门、这个时段获得有效办法。看见很多码也可能意味着还要逐个尝试，失败会更不信任产品。

价值排序：公寓匹配正确 → 资料当前可用 → 获取速度快 → 需要时才展开历史 → 我知道正确值时能快速修正。

### 2.2 配送中途

我主要停留在承运商 App。Abasong 的冷启动、定位、网络、键盘、弹窗及回到原 App 的成本都会侵蚀价值。反复登录、读公告、权限不够时只给设置跳转，都会让第二次打开变少。

因此首版应优先保证前台恢复、保存阅读对象、无精准定位时可搜地址、错误后保留输入，而不是增加连续后台定位或多层驾驶舱。

### 2.3 需要别人接手

我想把具体的一批工作交出去，不是把任务表格填完整。别人愿不愿接，取决于价格、取件点、还剩多少、是否理货、送到哪里及多晚结束。若我已经焦虑，发完帖子仍不知道有没有真实人看过，会继续回微信找人。

平台价值是更快触达适合的人、收到有条件的回复、及时联系。不是要求我再完成一套分配、交接、配送和结果上传。

### 2.4 提前送完或休息时

我可能愿意接顺路的额外任务，但不想为了小单反向开很远，也不想下班后还被当作有空。社区能增加归属，但它不是我在公寓门口下载 App 的首要原因。

租车、保险等内容可能有用，但第一版未必需要专门的交易和服务频道。普通同行图文与联系可以先满足一部分需求。

## 3. 如果站在 DSP 的位置

我不是在购买一张司机地图，而是在解决某个时间窗的缺口：**今天能来、愿意跑、适用这条线路、能联系上。**

### 3.1 四步缺一不可

1. 看见人：存在潜在人选。
2. 联系上：消息看到了、愿意回应。
3. 条件匹配：区域、时段、价格、容量与启用条件成立。
4. 形成合作：双方约好，随后愿意再次合作。

地图很擅长第 1 步，但不能自动解决后 3 步。注册数、在线点位、浏览数不是替班成功。

### 3.2 真正的储备库应带“可用性”

静态通讯录会过期；人可能转行、换城市、只跑熟线或白天有其他工作。“以前在某公司送过”不足以说明明早六点能到这个仓库。

DSP 最少需要：愿跑区域、最近确认的可接时段、相关经验来源、可用车型/容量、可联系渠道，以及是否已经合作过。它们能服务长期关系，不需要完整简历、工资或绩效管理。

### 3.3 为什么愿意再次使用与付费

如果平台反复带来原本联系不到的人，减少一轮轮群发和打电话，并让靠谱人选下次仍能找到，就有服务价值。

若平台只是把已认识的十个人再放一遍，或总是报名却无法约好，即使界面更好看也未必值得付费。发起人判断“200 以内愿付”仍不是成交证明，币种、周期和实际付款需分开验证。

## 4. 被忽视的司机痛点与细节

| 问题 | 当前容易漏掉的地方 | 影响 | 建议处理 | 优先级与证据 |
|---|---|---|---|---|
| 信息过时 | 旧码历史有用票很多，新码未积累票 | 一直优先展示已经不合时宜的码 | 在现有排序上研究反馈有效期与最近实测，不直接用历史总票证明今天可用 | P0 数据质量；逻辑推断，需试点验证 |
| 多门、多时段 | 相同公寓内可能不同门码或有时段限制 | “码正确但这次不适用”被误报 | 有必要时增加极简适用门/时间，默认不放复杂入口说明 | P0 按需字段；结合进入系统特点推断 |
| 没有固定密码 | 数字进入、前台登记等 | 用户连续试多个无效数字 | 资料模型支持进入方式；首页仍简洁，不立即做解锁集成 | P0 模型、后续合作；Amazon Key 支持模式存在 |
| 定位错栋 | 精确权限也可能漂移，沿街有多个公寓 | 快速拿到错误地址的密码 | 可信匹配才自动显示，保留不是这栋和手动搜索，阅读中不切走 | P0；Android 官方文档与现场逻辑 |
| 时间损耗转移 | 登录、冷启动、弱网、找菜单耗时 | 下载了也不愿第二次用 | 真机测试从原 App 切回到看到码，少弹窗，失败保留上下文 | P0；历史竞品评论支持交互摩擦 |
| 没资料 | 高频查询的区域覆盖不到 | 一次没用后卸载 | 先覆盖真实线路的困难公寓，明确暂无及快速贡献，不先铺全国 | P0；竞品评论+冷启动推断 |
| 不愿贡献 | 忙、没收益、提交太复杂 | 资料库只有消费没有更新 | 反馈与贡献低成本，解释状态，提供个人贡献记录；不强制拉人和贡献换查询 | P0 最小闭环；待测贡献行为 |
| 救援并不划算 | 件价高但空驶、等待、理货时间长 | 同价报名仍低 | 首屏报价旁说明区域、时段、是否理货和件/停靠点差别 | P0 核心条件；用户价格敏感观察支持 |
| 不顺路 | 离当前位置近，但偏离下班方向 | 地图距离近也不愿接 | 允许可接区域/最晚结束时间，不做完整路线优化 | P0 简单偏好；频率待测 |
| 部分承接 | 能接 30 件，不代表能接全部 150 件 | 有潜在供给却匹配失败 | 报名带可接数量，发布者能标剩余缺口，不强制自动拆线 | P0；用户实际救援场景 |
| 陌生主体与条件变动 | 谁发的、谁负责联系、价格被改 | 不敢报名、怕被骗 | 可识别联系人、组织来源、原发布条件及变更留痕；不扩成结算服务 | P0 信任；频率待测 |
| 包裹保管与车辆故障 | 修车与谁能接走包裹是两类问题 | 车修好前配送仍中断 | 首版优先配送接手；车辆求助只做同行联系，不承诺专业维修 | P0 接手、P1 专业服务 |
| 电量与隐私 | 额外 App 常驻定位、公开位置 | 手机续航与用户信任受损 | 前台必要定位、主动可用到期、避免持续轨迹 | P0；平台定位约束与产品边界 |

停车、上楼、电梯、楼号、包裹室同样可能影响效率，UFL 有相关研究。但这不意味着现在就把它们加回首页。只有当它们反复导致密码被误用或配送受阻时，才以可选补充信息处理，不能推翻已确定的简单主界面。

## 5. 被忽视的 DSP 痛点与细节

| 问题 | 关键细节 | 最小解法 | 暂不建设 |
|---|---|---|---|
| 所有人同时忙 | 爆仓往往不是单家，附近未必有闲人 | 真实可接时段与数量；提前发布预约需求，分开统计淡旺季 | 用更多假在线点位制造供给 |
| 看见与联系脱节 | 没看消息、无法及时回应 | 基础站内私聊、参与需求提醒、可选交换电话/微信 | 全渠道客服平台 |
| 承诺模糊 | 有兴趣、报名、约好不是同一步 | 明确报名内容、已联系/发布者称已约好/关闭 | 强制到场追踪与惩罚分 |
| 经验适用性 | 快速跑独栋不等于熟悉公寓；旧账号不代表可用 | 自报线路类型、熟悉区域、最近合作/确认时间，必要准入双方核实 | 读取原公司账号或全行业能力评分 |
| 招募帖失效 | 已找到仍显示缺人，取消后还接报名 | 剩余人数、到期、关闭；关联地图和动态同源 | 复杂招聘 ATS |
| 来人不匹配 | 车辆装不下、到场太晚、不了解取件流程 | 车型/容量、到场窗口、理货状态、仓库区域 | 全量证件库和背景核验公司 |
| 下次还得重新找 | 合作形成后没留下关系 | 双方同意的常联系、区域标签和再次邀请 | 员工所有权、排班薪酬系统 |
| 价格与成本 | 剩余件难、临时加价、等待与赶路 | 报价及条件透明，可补贴说明，双方协商 | 平台统一定价与自动涨价 |
| 组织真实与权限 | 普通司机替某 DSP 随意发招募 | 组织与具体联系人明确、代表发布需授权 | 全企业共享员工私人会话 |

## 6. 我们目前最需要修正的产品假设

### 6.1 “有用优先”需要补充时间有效性

现有规则是有有效有用反馈在前、同组贡献时间倒序。这比只看新增时间更有依据，但如果“有效”实际意味着任何年代都算，旧码仍可能长期挡住新码。

建议保留用户已确认的主规则，进一步区分贡献时间、最近实测可用时间、最近不能用时间及反馈适用门/时段。近期负面反馈应触发复核，而不是让历史正票永远压住它。

“有用”应定义为用户实际尝试且帮助进入，而不是泛泛点赞。可以绑定最近查看的该条记录，减少误投；但地理位置和一次点击不能被宣传为客观验证。

有效时间窗与降级规则还未确定。可以观察 7 天、30 天等不同分层，结合公寓更新记录比较，不能未经数据把某个天数定为行业标准。本轮不擅自改排序代码。

### 6.2 “司机多，密码就多”缺少覆盖与贡献条件

新司机如果跑不同区域，未必增加当前线路价值；一个人能分享的信息也未必有权跨平台传播。因此更合理的早期目标是同一批困难公寓反复获得可靠维护，而不是先追求全美注册量。

### 6.3 “附近的人”未必是最适合的人

服务区域、可到时间、报价接受度、剩余容量和相关启用条件比单一距离更重要。地图保留，但不能用地图代替筛选与联系。

### 6.4 “私下结算”不等于可以忽视信任

平台不做对账、付款确认、欠款或债务裁定；同时应保留真实联系主体、用户有权访问的原报价和条件变化，以及举报虚假任务、冒用和骚扰的入口。它们是信息服务的可信性，不是重新加入结算系统。

### 6.5 “社区让人留下”不意味着首版要做完整生活平台

司机圈可先提供与工作相关的互助、需求和少量图文。租车/租房/买车/保险可先作为普通标签，不制作四套专门流程；这类内容会带来广告、骚扰和诈骗审核成本，也可能淹没正在找人的帖子。

## 7. 第一版最优先的功能

### 7.1 司机现场工具

1. **真实公寓识别与手动纠错**：接真实定位和地图候选，测试错栋；自动显示、搜索及切回原 App 顺畅。
2. **有来源和新鲜度的进入信息**：当前资料、历史记录、贡献、逐条有用/没用、状态与撤回；后台能修正和处理，不只是前端展示。
3. **贡献的最小流程**：地址自动带入、少填、失败保留、不能覆盖其他记录，防重复和刷反馈。

这三项必须一起成立。只有漂亮卡片而没有可用资料，没有实际价值；只有大量码而没有匹配和维护，也会伤害信任。

### 7.2 司机与 DSP 的连接

4. **清楚的救援/线路需求**：区域、时段、数量/人数、报价、是否理货、联系人和私下付款约定。
5. **可用意向与最小经验档案**：区域、时段、容量、经验来源；主动开启、到期停止，不假装实时司机。
6. **报名与可靠联系**：能说几点到、接多少；基础文本私聊与需求卡片，必要通知或主动联系交换，不需完整社交 IM。
7. **关闭和再次合作**：剩余名额、已找到/关闭/过期、常联系与再次邀请，避免平台被旧帖和过期人选填满。

### 7.3 看不见但必须有的基础

账号与主体基本核实、使用权限、数据最小化、内容撤回、举报、反骚扰、操作留痕、运营修复。这些不应被做成首页提示段落，但不能因清理 UI 备注就从后台消失。

## 8. 首版后置或不做的功能

| 功能 | 建议 | 原因 |
|---|---|---|
| 地图中所有司机实时移动 | 后置 | 冷启动、耗电、隐私与陈旧状态；先展示主动可用服务区 |
| 租车/房屋/车辆/保险专用流程 | 后置 | 可先用普通帖子与联系，垂直交易复杂度高 |
| 专业道路救援平台 | 不作为首版承诺 | 需要真实服务供给与响应能力；先做同行求助和配送接手 |
| 群聊、语音、视频与直播 | 后置 | 先验证需求能联系上；不复制微信全部能力 |
| 复杂评分和排行榜 | 后置 | 样本小、难度不同、自报数据难验证，易误伤 |
| 自动拆线、自动派单与动态定价 | 后置 | 没有稳定有效供给和合法接口，算法解决不了结构缺口 |
| 司机版/DSP 版与工作台 | 不做 | 统一端已确认，角色操作重叠 |
| 承运商扫描、POD、路线系统 | 不做 | 用户已有原 App，重复建设会增加工作 |
| 配送结算与付款信誉 | 不做 | 明确边界，不能借信任之名悄悄恢复 |
| 20 次查码后立即付费 | 首发不做 | 先验证资料覆盖与即时价值；历史评论提醒收费摩擦，但不证明永远不能付费 |
| 全部 49 个设计节点同时开发 | 不建议 | 节点含状态与弹层；仍需按核心闭环分批，而非文档写了就都首发 |

保留三个底部导航和三地图视图，不等于每个视图都需要复杂系统。首版可用轻量资料、工作信息和联系人实现；空数据明确表达，不为了“看起来完整”填满虚假点位或功能。

## 9. 可直接用于收敛原型的决策

| 保留的已确认结构 | 建议简化的实现 |
|---|---|
| 首页公寓/找活/找人 | 公寓可靠识别；找活开放需求；找人仅主动可用服务区 |
| 收起卡与展开密码历史 | 摘要直接有用，展开才反馈；补充新鲜度逻辑与数据维护 |
| 独立发需求 | 配送找人为核心；车辆/其他保留简单联系，不许诺专业救援 |
| 司机圈生活与见闻 | 基础图文和标签，首发以互助/工作为主，不做交易平台 |
| 我的与组织资料 | 档案、可用、发布报名、贡献、常联系；没有工作台和财务 |
| 消息中心 | 文本、需求卡、必要通知；语音、群聊、企业共享收件箱暂缓 |

## 10. 两周真实验证：验证产品，不重复证明痛点

目前预览未接真实定位、密码库和在线匹配。下一步不需要再问“你有没有进不去”，而应测试能否解决具体一次卡门。

### 10.1 公寓样本

从真实常跑线路选择约 20–50 栋确有进入障碍且资料有权使用的公寓，覆盖相邻楼、多个门、频繁更新与弱网。数量为试验建议，不是统计代表性。

记录：从原 App 切回到见卡的耗时、匹配是否正确、是否有可用信息、哪条实际能用、无资料与错误是否可修复、司机是否自然再次使用。手机型号、权限、网络及楼宇不同分别记录。

首要区分：没识别到、识别错、没资料、码失效、操作不清楚。它们需要不同修复，不能用一个“失败率”掩盖。

### 10.2 DSP 与任务样本

从现有约 10 位 DSP 联系人中选择愿意发真实需求且按约合作的若干位，记录真实发布、报名、联系、约好与自报找到人。无需要求司机上报所有官方配送数据。

重点标原因：时间不合、价格不合、距离不合、容量不足、资格待办、联系不上、岗位已满、临时变动。若发帖多而约好少，先修条件和供给，不能立刻归因 UI 不够漂亮。

### 10.3 观察标准

公寓：覆盖正确、可用反馈、错误修复、真实复用；DSP：重复发布、联系与合作、合适司机复用；司机：任务条件清楚、有效响应、顺路性与时间成本。

软件收入必须有真实付费且无全额退款，不把说愿意付算收入。平台不采集私下到账与欠款，不用结算数据衡量平台闭环。

## 11. 价值与经济性表达

### 11.1 给司机

“我到公寓门口卡住时，这个 App 能更快给我可靠信息；我送不完或有空时，它能帮我联系合适同行。”

核心价值是节约等待和无效沟通、降低走错与试错、提高按预期收工的确定性。它不保证增加收入，也不保证任何任务都有人接。

假设一天有 4 次进入障碍，每次净节约 4 分钟，则节约 16 分钟；这是计算示例，不是研究结果。若总件数固定且最终都送完，节约首先表现为更早收工，并非自动多赚 16 分钟的钱。

### 11.2 给 DSP

“我缺人的时候能更快找到符合条件且愿意回应的人，合作顺利后下次还联系得到。”

价值是缩短找人时间、增加可用候选、减少空缺与反复沟通，以及积累重复合作。是否避免罚扣和损失需要具体合同与真实事件支持，不凭空估计。

### 11.3 平台的可持续价值

司机通过高频现场工具获得帮助，DSP 通过低频但紧急的用人场景获得价值。两边可互相带来网络，但不能让司机承担无效任务推送或让 DSP 为一张空地图付费。

潜在壁垒是某一区域持续可用的资料、愿意协作的人与可重复建立的信任。地图、按钮、普通聊天及分类本身容易复制。

## 12. 最终建议与本轮未执行事项

**继续项目；缩小首发承诺，先证明两个结果：司机在真实公寓门口确实少等，DSP 在真实缺口中确实联系到合适的人。**

首版不是“司机的全部工作和生活平台”，而是有清楚扩展方向的现场工具与轻量用人网络。社区可以保留，但其功能投入应服从真实使用证据。

本轮只形成研究与取舍建议，没有删除用户已确认的地图结构，没有改变已确认排序，没有擅自收缩或扩展现有原型。若采纳，应先将“反馈新鲜度、首发资料覆盖、最小合作条件、有效联系和过期处理”回填 PRD，再调整开发批次。

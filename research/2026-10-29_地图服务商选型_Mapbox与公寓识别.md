# Abasong 地图服务商选型：Mapbox 与公寓识别

日期：2026-10-29。状态：官方文档核查完成；尚未进行带 API 账号的洛杉矶实地对照，不宣称某家在本地精度领先。

## 1. 结论

**建议将 Mapbox 作为首版地图与地址能力的默认技术路线，自有公寓与进入信息库作为产品核心；Google 作为独立对照候选，不默认混用其 Places 数据。**

理由是可定制地图与自有图层、公寓建筑类型及轮廓、地址能力和产品交互契合。用户观察 SwiftX、GOFO、UniUni、SpeedX 使用 Mapbox，是有价值的一线输入，但本轮未逐一取得其官方架构说明，也未据此推导准确率优势。

“Mapbox 更精准”目前没有本地对照证据支持。正式上线前，应使用同一批真实公寓与设备验证自动识别，而不是比较地图外观。

## 2. 将“精准”拆成五个环节

| 环节 | 负责能力 | 可能的错误 |
|---|---|---|
| 手机在哪里 | OS 定位、权限、设备与环境、SDK 设置 | 粗略位置、漂移、旧位置 |
| 地址在哪里 | Geocoding、地址标准化 | 街道中心/插值点与实际公寓有差别 |
| 这是什么建筑 | 公寓类型、POI、建筑几何 | 公寓只标成一般 building 或住宅用途 |
| 当前位置属于哪个公寓 | Abasong 匹配、几何、候选与人工纠错 | 临街门、停车场、多个相邻公寓误匹配 |
| 应显示哪条进入信息 | 自有资料、适用范围、新鲜度与排序 | 旧码、错误门别、来源与授权不成立 |

Mapbox SDK 能接收设备位置并显示，iOS 指南也说明准确度权限与位置提供者。更换底图不等于自动改善 GPS；地址 rooftop 也不等于手机一定定位到该楼。[Mapbox iOS 位置文档](https://docs.mapbox.com/ios/maps/guides/user-location/)

## 3. Mapbox 已核实能力

### 3.1 公寓与建筑轮廓

Streets v8 有建筑轮廓，`building` 图层的 `type` 可取 `apartments`；同一字段也可能只是 `building`、`residential` 或其他类型，取决于来源与标注。可支持公寓样式、高亮与点击候选，但不保证洛杉矶所有公寓标注完整。[Streets v8 数据参考](https://docs.mapbox.com/data/tilesets/reference/mapbox-streets-v8/)

实现建议：显式选择并验证包含 Streets v8 数据的自定义样式/图层。不要未经核查就假设 Standard 样式的内部图层、字段与 Streets v8 完全一致。客户端可查询已加载渲染要素，但它不是覆盖全城市的永久空间数据库。

### 3.2 地址与搜索

Geocoding v6 支持地址正反查、美国子地址及结果匹配信息；它不再提供 POI 搜索，POI 使用 Search Box。`secondary_address` 表示单元等子地址，不等于“公寓类型”字段。建筑入口能力在文档中仍标为 public preview，不作为首版可靠性的唯一依赖。[Geocoding v6](https://docs.mapbox.com/api/search/geocoding/)

Search Box 支持地址、地点与 POI 交互搜索，也有类别搜索。本轮未带账号验证公寓专用 category ID 与本地覆盖，不在 PRD 写死一个未经验证的搜索类别。[Search Box](https://docs.mapbox.com/api/search/search-box/)

### 3.3 长期保存与数据归属

| 服务 | 官方文档说明 | 本项目处理 |
|---|---|---|
| Search Box | 返回数据默认临时使用；需要保存位置资料时联系 Mapbox | 不批量搬进长期公寓库 |
| Geocoding Temporary | 不允许缓存结果 | 搜索请求与持久业务数据隔离 |
| Geocoding Permanent | 可按文档选择持久模式，有账号条件 | 对需保存的标准化结果采用允许的模式，并确认 App 跨用户公寓库场景及使用范围 |
| 自有资料 | 来自本人/有权方贡献和实地核对 | 自有公寓 ID、来源、位置证据、进入信息与反馈独立维护 |

`permanent=true` 不是任意转售或分发许可。价格页亦说明永久结果有业务使用范围限制；实际公寓库和对用户展示的授权应与服务条款/供应商确认。[Mapbox 价格及产品说明](https://www.mapbox.com/pricing)

自有 `apartment_id` 不直接采用瓦片 feature ID；供应商字段与映射作为辅助引用，记录来源及许可模式。这样能处理供应商更新、多个建筑属于同一公寓社区、用户纠错与未来更换地图。

## 4. Google 与 OSM 的定位

| 维度 | Mapbox | Google Maps/Places | OSM 数据 |
|---|---|---|---|
| 自定义地图和自有点位 | 适合本项目候选路线 | 也可实现，需单独设计评估 | 可作为数据来源，非完整托管服务 |
| 公寓识别依据 | 建筑 type/几何与自有资料 | 明确的公寓 Places 类型 | 社区维护的建筑用途标签 |
| 地址/POI | Geocoding 与 Search Box 分工 | 各自 API，字段与产品版本不同 | 覆盖、地址质量因区域而异 |
| 本地精度证据 | 待同样本测试 | 待同样本测试 | 待同样本测试 |
| 长期数据使用 | 临时/永久/具体产品须区分 | 缓存、使用与展示有产品限制 | 需要遵守对应数据许可，不等于 Mapbox 数据可按 OSM 许可自由取出 |
| 建议 | 首版默认路线 | 独立备选对照 | 有需要时补充，首版不默认多源拼装 |

Google 地点类型文档列出 `apartment_building`、`apartment_complex` 等。因此 Google 也是合理的公寓候选识别方式，不能宣称其没有相关能力。[Google 地点类型](https://developers.google.com/maps/documentation/places/web-service/place-types)

Google 的原建筑轮廓/入口 v3 文档已提示迁往 v4 的 SearchDestinations；后续评估不能沿用过期的 v3 示例。[建筑轮廓与入口文档](https://developers.google.com/maps/documentation/geocoding/building-attributes)

### 4.1 不默认采用“Mapbox 底图 + Google Places 公寓点”

截至本次核查，Google 服务特定条款 §14.2 限制 Places API 内容与非 Google 地图结合使用；§15 对 Places UI Kit 存在专门例外，不能把例外扩成所有 Places 内容自由混用。§6 对 Geocoding 亦有相应规定。应逐产品与合同判断，不能只加 Google logo 就认为所有混用都成立。[服务特定条款](https://cloud.google.com/maps-platform/terms/maps-service-terms)、[Places 政策](https://developers.google.com/maps/documentation/places/web-service/policies)

因此对照测试保持供应商结果独立显示与处理；若将来需要特殊混用，先确认适用授权与成本，不把它作为默认架构。

## 5. 首版推荐架构

```text
手机前台位置（精度、时间、权限）
        │
        ├─ 自有已核实公寓范围/地址快速匹配 ───────────┐
        │                                           │
        ├─ 未命中时调用允许用途的地址/公寓候选能力    │
        │     Mapbox Geocoding / Streets / Search    │
        │                                           ▼
        └─ 与 Mapbox 地图加载并行             Abasong 匹配层
                                            唯一可信 / 多候选 / 未知
                                                    │
                                                    ▼
                                       自有 apartment_id 与资料权限
                                                    │
                                                    ▼
                                     收起卡摘要 / 展开后的密码记录
```

1. 地图用于呈现，不阻止自有记录的并行查询；已知地点不必每次重新做付费外部查找。
2. 公寓、需求、可用司机分三个自有展示层，业务 ID 与供应商独立。
3. 密码不在公开地图 GeoJSON 或批量瓦片属性中；仅对当前允许查看的对象返回正文。
4. 候选分数综合位置新鲜度与精度、公寓范围、地址、来源可信度和人工纠错；最近点不是充分条件。
5. 未知不自动合并，多个候选让用户选；用户手动选定后锁定，阅读不被新 GPS 抢走。
6. 不通过道路吸附把行人的门口位置强拉回道路来“提升”公寓判断。
7. 保留 Mapbox 与数据归属标识，避免被底部面板遮挡。它们不是可因 UI 精简删除的备注。[归属标识要求](https://docs.mapbox.com/help/dive-deeper/attribution/)

## 6. 成本估算方式

官方价格页区分移动 Maps SDK 的 MAU、Web 的 map loads、Search Box 会话与请求、地理编码及其他服务。不能用一个 Mapbox 免费额度概括所有费用，也不把价格计算器初始显示 Free 当成实际项目零成本。

不在此冻结容易变化的单价。实施时按当天价格和账号合同生成预算，至少分开：地图、交互搜索、自动候选查找、持久化编码、可能的 tilequery、服务端、自有存储。

例：100 名司机 × 每天 20 次公寓查询 × 每月 22 天 = 44,000 次业务查询。这既不等于 44,000 次地图加载，也不必等于 44,000 次外部搜索。自有命中、前台实例复用和正确的请求策略会改变账单；数字是规模情景，不是已测实际用量。

不要每次 GPS 更新都查 POI，不要每个输入字符都创建独立搜索会话，不为了微小缩放反复初始化地图。只缓存被允许缓存的数据，自有记录与供应商临时响应分开。

## 7. 对照测试与上线门槛

### 7.1 样本与输入

由真实线路选择约 30–50 个有权使用的公寓，包含相邻建筑、多个地址同社区、临街入口、较远停车点、老旧地址、只有 building 类型、信号差场景。每栋保存独立核对依据，不把某家 API 的第一结果直接当标准答案。

用相同现场位置输入、地址与查询时机比较两家；另外在真实 iOS/Android、不同权限下测端到端。供应商返回结果、设备定位误差和自有匹配错误分别记，不混成一个“精准度”。

### 7.2 指标

- 公寓候选覆盖与 top-1 正确率；多候选回退后能否找对。
- 错误自动匹配率，尤其错误公寓直接关联密码的情况。
- 名称/地址完整、建筑类型为 apartments 的比例与缺失回退。
- 同一公寓能否稳定归到同一个自有 ID。
- 冷/暖启动到卡、地图可用时间、外部请求次数与预算。
- 弱网、拒绝精准定位、手动搜索、样式加载失败时能否完成查询。
- 持久保存、显示范围、归属标识是否按各产品规则实现。

建议采用“宁可请求一次候选确认，也不要自信给错公寓”的质量原则。具体数值门槛在标注样本及风险复核后冻结，不能将小样本零错报成全美准确率。没有 API 账号、真实清单和实机对照之前，不宣布测试通过。

### 7.3 改选条件

Mapbox 在首发区候选缺失或错误显著影响体验、授权不覆盖持久库用途、预算不可接受，或设备端表现不满足要求时，重新比较 Google 完整路线。不是先把所有供应商都接入，也不是因为已定 Mapbox 就拒绝改选。

## 8. 已完成与未完成

已完成：官方文档能力、关键字段、数据使用限制、计费维度、Google 混用例外核查，推荐架构与测试计划。

未完成：四家承运商 SDK 的逐一官方确认、API 账号开通、真实公寓清单核对、现场请求与性能对照、合同范围确认、费用支付和正式接入。当前原型仍是合成地图与资料，不因本次选型报告变成真实 Mapbox 应用。
